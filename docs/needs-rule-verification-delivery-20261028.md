## 现在的处理过程

生产 HTML/API 的 `/api/v1/needs`：模型抽取 → 原有归一化与契约整形 → 独立规则核验 → 生成待确认草稿 → 页面逐项核对异常 → 整体确认 → 推荐排序。

新增 `needs_verification.py`，规则版本 `needs-rules-v1`；不依赖 MockClassifier 的判断规则，不新增第三方依赖或模型调用。只在本地演示脚本使用 MockClassifier 产生可控的上游夹具；正式服务仍使用原有模型接入。

- 核对预算上下限/参考锚点、中文数字/金额单位、品牌包含和排除、存储门槛/单位、屏幕尺寸、七个维度的明确重要程度。
- 明确规则与解析值冲突时填入待确认建议；保留归一化后的原解析值、规则建议、关联原话和异常类型。
- 检查七维原话证据，区分未提及、不在意和数值门槛；复杂否定或已落在原文但规则不能可靠理解的偏好保留为待核对建议。
- 没有可靠来源的硬条件不直接当作已确认条件。互相矛盾的预算清空后追问；含糊预算沿用既有程序推断与明确回显。
- 异常逐项勾选之前，整体确认与推荐按钮禁用。条件修改撤销所有异常勾选及旧推荐确认；新一轮抽取开始即撤销旧确认，HTTP 429/失败也不会保留可导出的旧决策。
- 没有发现冲突只显示“未发现已覆盖类型的冲突”，不承诺已排除幻觉。

用户可直接修改建议，再核对异常。对规则不覆盖的硬条件，草稿可能清空并提示填写，属于保守降级；规则覆盖不是完整自然语言理解。
